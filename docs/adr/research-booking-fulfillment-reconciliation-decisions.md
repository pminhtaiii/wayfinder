# Booking Payment and Fulfillment Reconciliation Decisions

> Status: Accepted target architecture. This refines the authorize-then-capture flow in [research-payment-system-decisions.md](./research-payment-system-decisions.md). Numerical timeout tiers in the earlier discussion are not accepted policy.
>
> Grilling checkpoint: Complete. The accepted behavior is ready for implementation planning; open technical details below do not reopen these decisions.

The primary booking path authorizes the traveller's payment with Stripe, creates a Duffel instant order using the supplier's authoritative amount and currency through its balance payment method, then captures the Stripe authorization only after validated supplier confirmation. The customer and supplier payments remain separate financial legs; the deferred supplier hold-order product flow is out of scope.

## Outcome and recovery rules

- A **confirmed** supplier outcome requires validated supplier evidence and permits Stripe capture. A **definitively failed** outcome permits cancellation of the Stripe authorization. An **unresolved** outcome must be reconciled before capture, release, or another create attempt.
- A create timeout can mean either no order was made or an order was made and its response was lost. Do not assume same-key create replay is safe or invent a unique lookup from an offer/reference. Retrieve by a verified order ID when one is available; validate any discovered linkage before acting.
- If Stripe capture definitively fails after the supplier order exists, compensate by cancelling that order and persist the compensation outcome. If capture is ambiguous, reconcile Stripe first; do not cancel the supplier order until the capture result is established.
- Automatic reconciliation starts as soon as an outcome becomes uncertain and continues after escalation. The initial configurable operator-escalation threshold is 15 minutes after uncertainty begins, with earlier escalation when intervention is needed before the actual Stripe authorization expires. This is an operational policy, not a provider guarantee. Neither threshold proves failure or triggers a refund, cancellation, release, or create retry. Late validated evidence resolves the active case and removes it from the active queue while preserving audit history.
- Before a new supplier create, confirm the Stripe authorization is valid and has enough remaining time for order creation, capture, and the configured recovery margin. If authorization is insufficient before any supplier attempt begins, request renewed authorization and do not dispatch the create. If a supplier attempt is already unresolved, preserve and reconcile that attempt; do not start a new booking or another create.
- Operator actions recheck provider evidence, validate supplier-order linkage, resume the correct workflow, and record the actor, evidence, action, and outcome. Operators do not force success/failure or retry an unresolved order create.
- Every actor that intends to mutate an unresolved case, including the automated reconciler and an operator, acquires the same time-bounded claim. After claiming, the actor re-reads and validates persisted state before any provider call or state change; an already-resolved case is a no-op. Expiry allows recovery after a crash or stall, so ownership cannot block a booking permanently. Reuse or extend saga ownership where feasible instead of adding a second locking model. The invariant is one currently authorized actor advancing or compensating a case at a time; claim expiry alone does not stop a stale in-flight provider operation or guarantee provider exactly-once behavior.
- Optimize unnecessary database round trips, not durable recovery evidence. Preserve existing checkpoint semantics and placement, and reuse a checkpoint only when it reliably covers the provider dispatch that follows. Where safe, replace a pre-provider ownership `SELECT` with an ownership-fenced attempt `UPDATE`, targeting roughly the same round-trip count without promising exactly one round trip. For an uncovered side effect, persist its attempt immediately before that specific provider call, after preflight validation. The marker means prepared or possibly sent; it does not prove the provider received the call. A takeover reconciles an unfinished attempt before replay. A crash before send and a lost response remain indistinguishable, so ownership fencing remains required.
- Give each logical provider operation a durable identity that remains stable across customer requests, automated recovery, and operator takeover; record each execution as a separate attempt. The identity belongs to the workflow operation, not an incoming HTTP request key or the current owner. Taking ownership does not authorize a new supplier create or establish that the provider safely replays one. Reconcile the prior attempt before choosing any follow-up action.

## Open implementation details

The exact claim mechanism, duration, renewal, and fencing behavior; Stripe-expiry margin formula; polling and backoff cadence; final contract types and error classification; provider reconciliation capabilities; sandbox account support; durable operation/attempt schema and update primitive; and identity generation or derivation details remain implementation/provider-validation work. The margin formula is not a user decision blocker. Queue-capacity warnings are deferred.

## Current implementation

A balance-payment mapping correction exists in the original working checkout but is uncommitted and absent from this planning-only development baseline; implementation tasks must integrate and verify it. The ambiguous create and capture recovery paths are still unsafe; this record describes the target behavior, not completed implementation.
