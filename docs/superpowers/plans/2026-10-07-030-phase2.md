# Feature 030 Phase 2: Durable Fulfillment Journal and Controlled Harness

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to execute this plan one task at a time. Each plan task is a fresh assignment with no more than two original Feature 030 task IDs. Each checkbox is a TDD checkpoint.

**Goal:** Build the additive, disabled-by-default workflow journal and the isolated provider test harness specified by Feature 030 Phase 2 tasks T003–T016.

**Architecture:** PostgreSQL stores one workflow/claim row per enrolled booking intent, stable provider operations, per-execution attempts, and immutable PaymentEvent evidence. A single database-time fence authorizes writes; provider requests remain outside transactions. Stateful Stripe and supplier simulators are reachable through their real HTTP/SDK transports, while a separate loopback-only driver owns test control and isolated run resources.

**Tech Stack:** Existing TypeScript/NestJS API, Prisma/PostgreSQL, Redis, Next.js 14.2.3, Playwright 1.62.1, Stripe Node SDK 15, Duffel SDK 4, Node test/HTTP libraries. Add no runtime or test dependencies.

**Spec:** specs/030-fulfillment-recovery-acceptance/spec.md; design detail in plan.md, data-model.md, contracts/provider-operations.md, and contracts/controlled-test-harness.md.

## Global Constraints

- Execute only original tasks T003–T016. T001–T002 are complete; T017 and later are out of scope.
- FEATURE_FLAG_FULFILLMENT_RECOVERY remains false by default and is never enabled by this phase. Ordinary feature-off booking/payment traffic keeps its current path; do not add capture, supplier creation, cancellation, release, refund, reconciliation, or operator behavior.
- PostgreSQL is authoritative for workflow, operations, attempts, claims, and evidence. Never hold a transaction open across a provider call.
- FulfillmentWorkflow is the only claim authority. Claim acquire/renew/write predicates use PostgreSQL time, owner token, and monotonically increasing fence. Lease expiry does not stop a provider call.
- A ProviderOperation keeps the same identity across requests and takeovers; every dispatch or reconciliation execution gets a new ProviderAttempt identity.
- PREPARED means possibly sent. It is never evidence of provider receipt or absence. Unknown supplier create is never replayed by this phase.
- Make persistence additive. Payment.stripePaymentIntentId becomes nullable while remaining unique for non-null IDs; RESERVED is internal. Existing ready-intent response fields and values remain compatible; an unready reservation returns safe pending information and no client secret.
- Stale responses may append immutable, sanitized evidence linked to their attempt. A stale owner never advances workflow, operation, checkpoint, booking, payment, or compensation state.
- Keep supplier balance amount/currency separate from traveler amount/currency. Controlled fixtures deliberately use different values.
- Keep Stripe and Duffel SDK objects inside existing adapters/ports. Simulators intercept the real HTTP/SDK transport. Do not override PaymentFulfillmentSaga or other application orchestration in composed tests.
- Keep test driver credentials out of API/web processes and browser bundles. Simulators bind to loopback only, reject other run IDs, and expose independent provider ledgers only to the driver.
- Persist no PAN, provider secrets, authorization headers, client secrets, passport/contact payloads, or raw provider payloads in workflow evidence or test artifacts.
- Do not add type assertions or any; use runtime narrowing. Inject Nest services through constructors.
- Use existing dependencies and native Node HTTP/test APIs. Do not install packages.
- Run each original T00x task through RED, GREEN, and its own commit. A RED-only test commit is a checkpoint, never a completed task. Mark paired test/implementation tasks complete only after the focused test is GREEN.

## Shared Interfaces

Task 1 prepares null-safe readers before Task 2 regenerates Prisma types. The later tasks use these exact interfaces:

~~~ts
export type WorkflowActor = {
  kind: 'SAGA' | 'RECOVERY' | 'OPERATOR';
  actorId: string | null;
};

export type WorkflowClaim = {
  workflowId: string;
  bookingIntentId: string;
  ownerToken: string;
  fence: bigint;
  leaseExpiresAt: Date;
};

export type NormalizedProviderOutcome =
  | 'CONFIRMED'
  | 'DEFINITIVE_FAILURE'
  | 'NONFINAL'
  | 'UNRESOLVED';

export type SafeProviderEvidence = {
  providerStatus: string | null;
  providerEventId: string | null;
  evidenceSource: 'HTTP_RESPONSE' | 'AUTHORITATIVE_READ' | 'WEBHOOK' | 'CANDIDATE_DISCOVERY';
  linkage: {
    bookingIntentMatched: boolean;
    offerMatched: boolean;
    passengerSetMatched: boolean;
    itineraryMatched: boolean;
  };
};

export type ClaimResult = WorkflowClaim | null;
~~~

FulfillmentWorkflowRepository consumes a bookingIntentId and WorkflowActor, and produces one ClaimResult from acquireClaim; renewClaim accepts a WorkflowClaim and returns one ClaimResult. Its fenced transaction helper locks/validates that same workflow row using ownerToken, fence, and clock_timestamp() before local database writes. Provider calls are always after the helper returns.

ProviderOperationService consumes a WorkflowClaim and produces a stable operation reference, a fresh attempt reference for each execution, and an evidence result. Its reservation input is {bookingIntentId, idempotencyKeyId, attemptNumber, amount, currency, stripeCustomerId}; prepareAttempt takes {claim, operationId, kind: 'DISPATCH' | 'RECONCILIATION', requestFingerprint}; recordOutcome takes {claim, attemptId, outcomeClass, eventType, providerObjectId, amount, currency, observedAt}. It returns ADVANCED only when the current fence advances local state; otherwise it appends evidence and returns EVIDENCE_ONLY. ProviderOperation uniqueness is [workflowId, provider, purpose, logicalSequence], independent of HTTP keys and claims.

The simulator contract is the existing controlled-test-harness contract: provider servers accept only application-facing simulator credentials; the driver uses a separate credential. Allocate returns {runId, frontendUrl, apiUrl, providerUrls, applicationCredentials, driverToken} in distinct fields. Release-event, release-response, advance-clock, scheduler-drain, inspect, and teardown routes are driver-only and run-scoped.

The exact repository contract for T007 is:

~~~ts
export type ClaimWriteResult<T> =
  | { kind: 'APPLIED'; value: T }
  | { kind: 'FENCED_OUT' };

export interface FulfillmentWorkflowRepository {
  acquireClaim(
    bookingIntentId: string,
    actor: WorkflowActor,
    leaseMs?: number,
  ): Promise<ClaimResult>;
  renewClaim(claim: WorkflowClaim, leaseMs?: number): Promise<ClaimResult>;
  runFencedTransaction<T>(
    claim: WorkflowClaim,
    write: (tx: Prisma.TransactionClient) => Promise<T>,
  ): Promise<ClaimWriteResult<T>>;
}
~~~
runFencedTransaction must lock/check the single workflow row and require matching workflowId, ownerToken, fence, and leaseExpiresAt > clock_timestamp() in PostgreSQL in the same transaction as write. acquireClaim atomically increments fence once only when owner is empty or expired by clock_timestamp(); the lease duration comes from the explicit positive integer argument, default 180000ms. Renewal keeps the fence and uses DB time. Provider requests never run inside write.
